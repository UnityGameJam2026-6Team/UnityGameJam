# AI 워크플로우 안내

> 이 프로젝트에서 사람 2명과 AI 에이전트 2개가 어떻게 함께 일하는지 설명하는 문서다. 사람이 읽는 안내서다.
> 에이전트가 따르는 **규칙의 원본**은 `AGENTS.md`와 `docs/rules/`에 있다. 이 문서와 규칙 문서가 다르면 규칙 문서를 따르고, 이 문서를 고친다.

## 1. 한눈에 보기
```
            기획 (Assets/GDD/)
                  │
        ┌─────────┴─────────┐
   김보경 + Codex       심지섭 + Unity AI
   A 레인: 규칙·시뮬레이션   B 레인: 월드·표현
   (순수 C#, 테스트, 데이터)   (씬, 프리팹, UI, 입력, 아트)
        │                    │
        └──── 계약 (Runtime/Contract/) ────┘
                  │
        통합 지점 M1 → M2 → M3 (함께 확인)
```
- **같은 규칙, 다른 에이전트**: Codex는 `AGENTS.md`를 읽고, Unity AI는 프로젝트 스킬(`7_Setting/AI/ProjectRule/SKILL.md`)을 거쳐 같은 문서를 읽는다. 규칙은 한 곳(`AGENTS.md` + `docs/rules/`)에서만 고친다.
- **레인이 겹치지 않음**: 파일마다 주인이 한 명이라 병합 충돌이 거의 생기지 않는다.
- **에이전트는 추측하지 않음**: 기획에 없는 내용은 묻고, 묻지 못한 것은 문서에 기록한다.

## 3. 누가 무엇을 하나
| | 김보경 | 심지섭 |
|---|---|---|
| 레인 | A: 규칙·시뮬레이션 | B: 월드·표현 |
| 에이전트 | Codex (에디터 밖) | Unity AI (에디터 안, Agent 모드) |
| 만드는 것 | 청결도 계산, 오염 상태, 작업 선택, 졸개 두뇌, 제안 대기열, 판 흐름, 수치 SO | 시설 화이트박스, 플레이어, 졸개 이동, 오염 표시, HUD와 UI, 마감 연출, 아트 적용 |
| 소유 경로 | `Runtime/{Cleaning, Minion, Proposal, Match, Facility, Data}`, `Test/`, `3_Data/` | `Runtime/{Player, View, UI}`, `Editor/`, `Test/{Art, View}`, `1_Scene/`, `4_Prefab/`, `5_Art/`, `6_Audio/` 등 |
| 번호 대역 | 100번대 | 200번대 |

이렇게 나눈 이유: 씬, 프리팹 같은 YAML 파일은 병합이 어렵다. 그래서 그런 파일은 에디터를 직접 다룰 수 있는 Unity AI 쪽(B)이 모두 맡고, Codex 쪽(A)은 텍스트 C#만 다룬다.

## 4. 기능 하나를 만드는 순서
```
Roadmap에서 고르기 → 브랜치 → Spec 작성 → 검토(승인) → 테스트 먼저 → 구현 → View 연결 → DoD 확인 → Roadmap 갱신 → 커밋·PR → 상대 리뷰 → Squash 머지
```
1. **고르기**: `Assets/GDD/Roadmap.md`의 자기 레인 단락에서 다음 항목을 고른다. 브랜치 이름은 `feat/<짧은-영어>`로 짓는다.
2. **Spec 작성**: 에이전트가 `Spec/_Template.md`를 복사해 근거, 규칙(번호), 설계, 미결 질문, 테스트 시나리오를 쓴다. **별도 계획서는 만들지 않는다.**
3. **검토 1회**: 에이전트가 스펙과 미결 질문을 한 번에 보여 준다. 사람이 답하고 승인한다. **미결 질문이 남아 있으면 구현하지 않는다.**
4. **테스트 먼저**: 순수 C# 규칙은 테스트를 먼저 써서 실패하는 것을 확인한 뒤 구현한다. 테스트 이름은 한국어 문장이다(`시설이_90이어도_3층_로비가_59이면_실패한다`).
5. **View 연결**: MonoBehaviour는 규칙을 부르고 결과를 보여 주기만 한다. 에디터에서 플레이해서 확인한다.
6. **DoD**: 미결 질문 0, 규칙마다 테스트 통과, 콘솔 에러 0, 우리 코드 경고 0, 수치는 `3_Data`에서 읽음, `.meta` 포함.
7. **마무리**: 에이전트는 커밋하지 않고 커밋 메시지(`feat: …`)를 추천한다. 사람이 커밋하고 PR을 올리면 상대가 리뷰한다.

## 5. 에이전트별 사용법
### Codex (김보경)
- 대화를 시작할 때 레인을 밝히고 읽을 문서를 지정한다. `docs/team/lane-a.md`의 첫 프롬프트를 복사해서 작업 번호만 바꾸면 된다.
- Codex는 에디터를 직접 다룰 수 없다. 씬과 프리팹은 건드리지 않고, SO 에셋 생성처럼 에디터가 필요한 일은 에디터 스크립트를 만들게 한 뒤 사람이 실행한다.
- 테스트: 에디터가 열려 있으면 `Window > General > Test Runner > EditMode`에서 직접 실행한다. 에디터를 닫았다면 Codex에게 배치 모드로 실행하게 한다(명령은 `unity-editor.md`).

### Unity AI (심지섭)
- 에디터 안에서 Agent 모드로 쓴다. 프로젝트 스킬이 규칙 문서를 자동으로 읽게 한다. `docs/team/lane-b.md`의 첫 프롬프트로 시작한다.
- 씬, 프리팹, 에셋은 에디터 API로 직접 만든다. YAML을 텍스트로 고치지 않는다. 씬을 바꾸면 같은 명령 안에서 저장한다.
- 컴파일 확인, 콘솔 확인, EditMode 테스트 실행(TestRunnerApi)까지 에이전트가 직접 하고 결과를 보고한다.
- 여러 시스템에 걸친 큰 작업은 Plan 모드로 먼저 계획을 맞춘다. 승인된 계획은 `Assets/Plans/`에 남는다.

### 공통 요령
- **한 번에 한 작업**: 프롬프트 하나에는 Roadmap 항목 하나만 맡긴다.
- **근거를 짚어 주기**: GDD의 절 번호와 Undecided/DesignIssue 번호를 프롬프트에 적으면 추측이 줄어든다.
- **대화로 정한 것은 문서로**: 에이전트는 메신저를 못 본다. 정한 내용은 Spec, Undecided, GDD에 남긴다.
- **레인 밖 변경 확인**: 커밋 전에 "내 레인 밖 변경 파일이 있으면 알려 줘"라고 시킨다.

## 6. 두 레인이 만나는 곳: 계약
- `Runtime/Contract/`에 인터페이스와 데이터 구조가 있다. 주요 계약: `FacilityLayout`(씬 → 규칙), `IMinionBody`(규칙 → 졸개 몸), `IMatchCommands`(입력 → 규칙), `IMatchReadModel`(규칙 → UI), `MatchSessionFactoryBase`(Bootstrap 입구)
- **상대를 기다리지 않는다**:
  - A는 씬 없이 `FacilityLayout`을 테스트 코드에서 직접 만들어 쓴다.
  - B는 가짜 판(`FakeMatchSession`)으로 UI와 조작을 먼저 만든다.
- **계약 변경**: 메신저로 알린다 → `Contract/`만 고친 PR을 올린다 → 상대가 리뷰한다 → 머지하고 둘 다 main을 받는다.
- **통합 지점**: M1 오염이 보이는 맵 → M2 졸개 배정 플레이 → M3 3분 한 판 완주. 이때만 둘이 함께 확인한다.

## 7. 기록 남기기
| 상황 | 기록할 곳 | 코드 표시 |
|---|---|---|
| 기획이 정하지 않아서 임시로 정했거나 미룸 | `Assets/GDD/Undecided.md` (U번호) | `// TODO: 임시 (미정 U번호. 이름)` |
| 기획끼리 모순, 기획대로 만들면 문제가 생김 | `Assets/GDD/DesignIssue.md` (D번호) | - |
| 스펙과 다르게 구현하게 됨 | 스펙을 먼저 고친 뒤 코드를 고친다 | - |
| 큰 방향 결정 | `Assets/Plans/` 계획 문서 | - |

번호는 바꾸지 않고, 해결되면 상태만 바꾼다. 대역은 공통 1~99, A 100번대, B 200번대다.

## 8. 아트 에셋 흐름 (요약)
1. 아티스트는 이름 규칙(`docs/art-naming-guide.md`)에 맞춰 FBX와 텍스처를 내보낸다.
2. 심지섭이 파일을 `5_Art/Model/<분류>/<ArtKey>/`에 넣는다.
3. `Tools > UnityGameJam > Art > 검사`로 상태를 보고 `전체 적용`을 누른다. 화이트박스가 모델로 바뀐다.
4. 플레이해서 확인한 뒤 `art: <ArtKey> 모델 적용`으로 커밋한다.

## 10. 자주 묻는 것
- **에이전트가 다른 레인의 파일을 고쳤다**: `git restore <파일>`로 되돌리고, 프롬프트에 "소유 경로 밖은 고치지 마라"를 다시 넣는다.
- **Unity가 열기만 했는데 씬이나 ProjectSettings가 바뀌었다**: 의도한 변경이 아니면 되돌린다. 커밋 전 체크리스트에 있는 항목이다.
- **기획에 없는 걸 에이전트가 정해 버렸다**: 규칙상 묻거나 Undecided에 기록해야 한다. 스펙의 미결 질문으로 옮기고 답을 받은 뒤 다시 진행한다.
- **테스트가 에디터에서만 돈다**: 순수 C# 규칙은 EditMode 테스트라 에디터의 Test Runner로 돈다. 배치 모드는 에디터를 닫았을 때만 쓸 수 있다.
